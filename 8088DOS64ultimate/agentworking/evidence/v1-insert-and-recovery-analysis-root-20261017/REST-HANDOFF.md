Concrete route distinctions:

* `route_machine.cc:46–51,70–122` pause and PUT-hex memory write synchronously execute a C64 `SubsysCommand`. `infra/subsys.cc:15–28` uses its mutex with1000 RTOS ticks. A normal lock refusal maps to HTTP423, not a reset (`infra/subsys.h:192–202`). Normal malformed arguments/auth produce JSON400/403 (`api/routes.cc:73–100`). The two-byte SEQ request is within the documented PUT128/range/hex bounds; no upload/body/attachment is required.
* GET info directly emits inventory (`api/routes.cc:118–143`), and GET configs reads/serializes values (`route_configs.cc:163–185`), bypassing that C64 command path. Their success does not establish pause/write availability. GET `machine:readmem` **does** take the C64 command path (`route_machine.cc:171–199`); read and write share `dma_load_raw_buffer`, differing by memcpy direction (`io/c64/c64_subsys.cc:524–547`). Such a fresh RAM observation is stronger than inventory but remains an owned device action, requiring separate authorization.
* Config PUT has a separate path: enum matching →setValue→at_close_config (`route_configs.cc:63–90,188–247`), with a CPU-speed change hook (`u64/u64_config.cc:833–836,1208–1242`). There is no source-backed common “all PUTs share the C64 mutex” explanation.
* API response creation follows command execution. Lost acknowledgement leaves write/pause/config effects ambiguous. The retained transport already creates a fresh HTTPConnection per request, consumes bounded response bodies, closes in finally, preserves first error, and never retries ACKs (`numeric_transport.py:37–121`). Stale keepalive reuse is not present. No transport variant is justified by this audit.

Recovery limits: pause maps to `stop(false)`; reset maps to unfreeze/reset; reboot starts the configured cartridge (`c64_subsys.cc:183–237`). `C64::reset` pulses the C64 reset (`c64.cc:584–591`), not a documented REST-service restart. None of those handlers promises native FILES/CWD closure or safe unknown-handle replacement. The stop fallback may wait for a hardware stopped condition (`c64.cc:449–479`), so a host deadline is not cancellation of an already admitted operation. This observation does not explain the rapid Reset54 failures.

Actionable: preserve SEQ76's ambiguity and never resend it as an ACK retry; distinguish inventory health from fresh exact private WAIT/RAM proof; require CIA's source-bound cancel/CLOSE path and known quiet before any replacement/reset/profile step; stop at a fresh ambiguous response. Do not use POST, debug registers, repeated pause, configuration reset, or firmware changes as a workaround inferred from this note. No send-path investigation or stress experiment is proposed.
