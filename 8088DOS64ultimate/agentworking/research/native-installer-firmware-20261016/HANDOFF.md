# Native SETUP / fixed REU launcher: firmware findings

Research only, 2026-10-16. No Ultimate/LAN calls, firmware changes, ROOT edits, builds of project native code, or changes to older seals. Public upstream downloads and bounded host source-function controls only.

**Recommendation:** deliver SETUP.PRG and the fixed small launcher directly on USB, started using the Ultimate menu's native PRG Run/Load. SETUP should create an owned ordinary raw 20 MiB HD file with explicit Ultimate DOS OPEN and repeated SAVE_REU ($21/$22 on DOS targets $01/$02); stage one aligned 32 KiB zero buffer below the independently verified 4 MiB REU limit and reuse it **640 times**. Write the chosen PC FAT16/boot/system-file layout and application payload afterward, then CLOSE, reopen and verify the complete image. This is a source-supported candidate, not an installed-hardware acceptance or speed result. A small owned physical qualification must precede use.

“Native FAT16 format” here means C SETUP generates the **PC disk's** checked partition/BPB/FAT/root/system-file sectors, or emits an explicitly defined prepared sector template. The firmware's FatFs operates the USB host filesystem; UCI does not expose a PC FORMAT operation. Preserve an exact documented supported geometry (the current 20 MiB image uses CHS640/4/16), and validate the generated image through the existing raw backend and strict FAT tools. Dynamic creation does not require a custom container or a D81 launcher.

## Installer/launcher consequences

* 20MiB=20,971,520bytes=40,960sectors=640×32KiB. Reusing the same zero REU source span advances the **file** pointer each command; it need not consume20MiB REU. A separate readback buffer permits LOAD_REU and independent CRC/byte checks without destroying the reusable zero buffer. 81,920 is the corresponding256B WRITE count; the128× reduction is command count only, not a measured speed ratio.
* Bound every REU range to an independently established configured capacity of at least4MiB. Firmware DOS silently accepts some addresses beyond4MiB, strips a high address byte, and can turn a malformed high length into zero. `SOURCE_FACT_CHECKS.json` retains explicit arithmetic examples. Native 1764 DMA into/out of the buffer is a separate step and needs its usual banking/length/ownership checks.
* For a fixed launcher: OPEN known install payload, verify metadata/header/version/length, LOAD_REU complete bounded sections, validate exact counts and contents, finish/drain/CLOSE, then use an assembler trampoline outside every destination span to fetch to C64 RAM and enter once. Keep launcher/stack/trampoline/overlay ownership explicit. No standard DOS command here loads arbitrary PRG bytes into C64 RAM or starts them. The firmware menu's PRG loader handles entry of SETUP/launcher without D81; its boot-cartridge handshake is firmware-internal, not a callable UCI self-load protocol.
* Reuse ReadyOS's existing DOS21/22 transport/parser and launcher loading patterns where compatible, rather than adopting their app bank map or special image-clipping exception. `readyos/.../uz_dos.c` lines312–365 bounds bank spans, parses transferred count; `launcher_uci_dma.s` lines332–379 validates PRG header/seeks payload/loads REU; lines708–730 builds the10B command. Source provenance: ReadyOS-C64/ReadyOs commitbeb9dd3ff61521fa8ef17705bedf9733d84a81a2, selected files clean. They are references, not a proven DOS64 launcher.

## Raw file versus sparse/container

Keep ordinary raw512B sectors at file offsetLBA×512 (`project-reference/hd_cache.s` sector_offset519–532). A POSIX sparse file could read holes as zero on a suitable host; FatFs seek growth is **not** that guarantee and allocates the FAT chain. Skipping free DOS clusters can produce a valid raw disk if all metadata and allocated contents are explicitly correct, since free clusters need not be zero. It cannot reproduce an expected deterministic whole-image hash. Current canonical ac1 image already contains deleted CROSS16 data in free clusters; a newly zero-formatted disk is a different authorized image with its own fixture/hash, not byte-exact ac1.

A compact installer archive containing used extents plus desired image geometry is useful: expand it during SETUP to an ordinary raw file. A permanently sparse/custom HD container requires new read/write translation, missing-block rules, allocation/index recovery and tests; current raw backend, DOS reference tooling and strict image checks do not automatically support it.
