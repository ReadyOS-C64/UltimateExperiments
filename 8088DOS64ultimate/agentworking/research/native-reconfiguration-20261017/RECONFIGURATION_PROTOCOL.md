# Native reconfiguration: a new launch generation, existing media

Status: source-backed implementation proposal only. No target code, filesystem mutation, hardware access, ABI allocation, measured link or new model execution is claimed. Source identities are in SOURCE_PINS.json. Public main/START interfaces below are current; the memory agent's INI successor is explicitly provisional.

## Recommendation

Add a separate **Reconfigure an existing installation** mode. It creates a fresh launch folder with a matched runtime bundle, new configured START and new CFG, and references the selected existing A/B/C images by absolute path. It does not invoke NF/FAT creation or import, format or replace a disk, overwrite the current START/CFG, or pretend that an existing disk has a fresh-writer receipt. The user runs the new folder's START to activate it. Running the old START remains a rollback for launch configuration; shared writable media are not rolled back.

The first version can require an already-created empty destination folder, selected through the existing browser. Creating a folder natively is a separate small command-wrapper slice. Destination preflight is advisory; final CREATE_NEW remains authoritative. Reconfiguration must preflight all new runtime/config/option names, beyond the fresh install's five generated names.

Public CFG is D64C version 1, 576 bytes. The body identity is CRC over bytes 0..571 stored at 572..575; the CRC of the whole valid codeword is a fixed residue and cannot identify a particular configuration. New publication must bind the body identity and actual bytes, including the legitimate body-CRC-zero case.

## Concrete transaction and persistent artifacts

1. **Inspect original, readonly.** Startup-close both firmware targets through the accepted same-engine startup protocol. Select original home. OPEN/INFO/read exactly 576 bytes of DOS64.CFG, require EOF and known CLOSE, then validate native codec, home and padding. Retain a private inspection receipt (source path, byte count, body identity, session generation). Any public observations or stale REU record are insufficient. Never modify original CFG on parser or I/O failure.
2. **Choose destination and changes.** Select a fresh existing folder. Choose A and optional B/C canonical absolute files, supported profiles, configured REU capacity and readonly flags. Distinguish launch settings from media transformation. Display old/new home, all media paths and shared writable status before confirmation. An ordinary configuration rollback does not undo later writes to a shared image. Preserve old values by default; changing a referenced file requires explicit selection.
3. **Validate referenced media, readonly.** A/B: INFO exact 368640, staged full bytes with independent READ04 verification, fresh CRC, exact EOF/CLOSE. C: INFO exact supported raw 2/20 MiB size, readonly MBR/partition/BPB/geometry validation and known closure. Invalid or unsupported media fail before output creation. Do not do a full logical FAT import in this mode. Reads and verification are bounded cooperative clock/RunStop jobs, preserving first observed native cause and draining pending work.
4. **Validate matched release assets.** Select a qualified source release bundle. Verify full main and release descriptor, disabled START template and D64S descriptor using current checks. New output runtime files must be byte-for-byte copies of this verified bundle. The old main/release may be reused only if their exact accepted release/template match is established. No generic allowlist widening. No need to copy unchanged media. The matched main is currently 47105 bytes, START 18432, REL 64, CFG 576: 66177 bytes total, excluding optional INI overlay/text and future SETUP assets.
5. **Prepare small outputs privately.** Native CFG maker uses new home, selected absolute paths, actual media receipts and flags. START helper patches only its whitelist using that same home. Reconfiguration needs new private readonly-media facts rather than forged SI_DONE/NF-consumed/writer output-mask facts. Readonly references are a distinct producer capability. No overlaid callback pointer or UI frame survives a swap.
6. **Publish to new folder only.** Same engine and CREATE_NEW for every artifact. Suggested order: DOS64.PRG, DOS64.REL, any required matched START.INO and optional DOS64.INI, START.PRG, **DOS64.CFG last**. Each write requires exact count, full independent reopen READ04 comparison, EOF, known final CLOSE and private verified receipt. Recheck destination capability before CREATE. No rename or overwrite shortcut. Before CFG is valid, a new START must fail closed rather than fall back to old or stale config. Do not show successful completion merely because the last CREATE returned success.
7. **Activate explicitly.** Show the new absolute START path after all required outputs are privately verified and both handles are known closed. Run it only through a separately qualified native handoff or let the user launch it. Existing old START remains usable. A successful generated START must be tested through the actual matched main and genuine DOS commands with the selected external images. Old and new launch files must remain independently verified.
8. **Recover conservatively.** Cancel/error retains first cause and all partial new files; it does not reset the engine, silently delete files or overwrite the original. After reboot, reread and validate durable artifacts; a stale REU ready marker or a journal claim never proves completion. Initial recovery may simply offer inspection and a fresh folder. If implementing resume later, require exact source release, requested configuration, existing output bytes/lengths and private reinspection before skipping any step. Never “repair” a conflicting unknown file automatically.

An interruption during a filesystem metadata write may affect shared FAT metadata even when application code only creates new files. This protocol preserves the old installation at application level when the filesystem remains intact; it does not promise general power-cut rollback or filesystem transactionality.

## Native command support and why not swap the old CFG

Pinned local v3.14 dos.h defines DELETE=09, RENAME=0A, COPY=0B and CREATE_DIR=16. dos.cc lines 208–253 implements delete/rename/copy; 432–444 mkdir. COPY passes a destination directory and retains source filename; no arbitrary replacement semantics or independent verification should be inferred. Existing br/bc exposes none of these mutations, so a new wrapper must acquire the same UI lease only when both file targets are actually known closed, drain all queues, parse exact status and release only at verified quiet.

FatFs f_rename, ff.c lines 5190–5265, rejects an occupied new name, registers the new directory entry, removes the old entry and calls sync_fs. It explicitly marks interruption-sensitive cross-link critical sections. There is no source-supported atomic replace/swap primitive. CLOSE/sync success is not proof against all later power-loss/cache behavior. Thus keeping DOS64.CFG at the same path while switching in place needs a separate journal/recovery design, filesystem failure controls and physical qualification. A temporary file plus rename is not enough to claim atomicity. The fresh generation protocol avoids requiring that guarantee.

## Existing-C content update policy is separate

Current nf_import_dos unconditionally creates each supplied root file at DOS/DISK1..3 with replacement disabled. It creates DOS/name only if absent, preserving earlier convenience files. This preserves variants on a fresh build and deliberately refuses an existing archive collision; it does not compare identical bytes or permit automatic replacement.

If a later media-update mode is requested: readonly original -> new owned raw output, validated import tree, explicit per-file KEEP / REPLACE / alternate archive namespace, byte-compare before classifying “identical”, preserve all selected original variants and metadata. Never silently overwrite different archive bytes. The current library's explicit replace argument is not an implemented UI conflict policy. Logical import does not preserve original bootability, cluster placement, deleted entries or free-sector bytes. A raw clone or raw in-place update would need a different proven worker. Reconfiguration needs neither operation.

## INI coordination, without premature ABI adoption

As reported by the memory agent, public START still has fixed embedded home, DOS64.CFG and template/D64S ABI1 sizes 18432/131 bytes. Its private INI successor adds same-home DOS64.INI reread at every cold launch (initial_columns 40/80), a matching START.INO asset and D64I descriptor. The coupled private main uses D64L v2 and launch-bound D64O32 at 3FF500. These are not sealed/accepted when this note is written. Never distribute the old START with a new INO or assume a stale REU options record substitutes for a disk reread. Reconfiguration must select a complete qualified release; preserve unknown INI keys/text verbatim only under the accepted parser policy, or explicitly generate supported settings into a new file. No reserved public CFG bytes should be repurposed to carry unreviewed options.

## Next implementation interfaces and tests

Propose a UI-phase readonly `ri_begin(home)/ri_poll/state/error` inspector yielding an immutable native receipt, a separate verified-media reference job, and a reconfiguration PUB worker accepting those private capabilities and the matched release/template. The current fresh-installer PW fact callback must not accept synthetic writer receipts. Add the mode/capabilities without changing public D64C/D64R solely to support external paths.

Current post-terminal UI has 3060 bytes of measured spare; parent's in-progress preflight adds 495 UI bytes and 2 HIGH state bytes (31 remain). Do not assume a full native codec or new worker fits: full codec previously removed 1552 code +1728 BSS from UI; current PUB/FAT margins are 1/3 bytes. A validator-only profile exists in current codec source, but an actual reconfiguration link and lifetimes must be measured. Prefer a distinct checked reconfiguration phase asset or deliberate overlay refactor rather than pooling mutually live RAM. No additional resident budget is allocated here.

Required actual native controls: external A/B/C different-parent positive; CFG.home mismatch; readonly adoption; stale A/B old CRC accepted only after actual reread/new identity; malformed geometry/padding/alias; original directories and full files unchanged under each output collision; write/readback/count/EOF/CLOSE/clock/cancel failures at every output; identity-zero and wrong-body same-residue substitution; old/new release or INO mismatch; invalid/torn CFG-last blocks launch; stale REU marker cannot authorize; private receipt forgery; phase-retirement/no overlaid return; old/new generated START through genuine DOS. Directory mutation packet tests and physical command qualification are required if native mkdir is added. Power-cut tests must describe observed filesystem outcomes, not assume atomic rollback.
