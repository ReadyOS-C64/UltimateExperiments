Could a 64 MHz C64 Ultimate emulate an IBM PC running DOS 3.x or 4.x?
Yes, and I think it's a genuinely feasible engineering project. You could build something that runs real 8086 DOS programs on the C64 Ultimate, with up to 640 KB of emulated conventional memory, DOS file access, keyboard input, and text or limited graphics output.

The interesting question isn't whether it can be done. It's how much of a 1980s IBM PC's performance you can recover.

My assessment:

8086 CPU emulation: Very feasible, particularly if optimized in 6502 assembly.

640 KB of PC memory: Feasible with the 16 MB REU, but paging will be the biggest performance risk.

DOS 3.x compatibility: Feasible without emulating all the PC hardware.

DOS 4.x: Also feasible. It doesn't require a 286.

Performance: Approaching a 4.77 MHz IBM PC/XT is plausible for selected workloads. Consistently matching or exceeding one is much harder.

Development with strong agentic coding: Quite realistic, provided it is built and tested in layers rather than attempting complete IBM PC compatibility immediately.

The most promising design would be a hybrid 8086 emulator and DOS-compatible runtime, closer architecturally to early DOSBox than a complete virtual IBM PC.

Clock rates alone are misleading: a 6502 and an 8086 perform different amounts of work per instruction, and emulation adds considerable overhead.
The C64 Ultimate's 64 MHz mode provides approximately 13.4 host clock cycles per original XT clock cycle.

That's actually a useful starting budget. An 8088 instruction might require anywhere from a handful to many dozens of clocks, depending on the instruction and memory activity.

But to execute one x86 instruction, your 6510 emulator must decode it, identify its operands, calculate effective addresses, emulate the operation, and update the x86 status flags.

The result could require tens or hundreds of 6510 clocks for one x86 instruction, with particularly expensive cases taking considerably more.

A vital hardware distinction: the Commodore 64 Ultimate and Ultimate 64 Elite-II support 64 MHz; earlier Ultimate 64 boards top out at 48 MHz. The Ultimate documentation also confirms that accesses to internal memory can run at turbo speeds, while external hardware accesses may be constrained.

The crucial architectural decision is not to run the actual DOS kernel initially.

Instead, run DOS applications by emulating their CPU instructions and intercepting DOS/BIOS services. DOSBox uses this general technique, with emulator-native callbacks for DOS interrupt services.

A DOS application doing:

MOV AH, 09h
MOV DX, msg
INT 21h
wouldn't need the original DOS kernel executing thousands of additional x86 instructions.

Your emulator would recognize INT 21h, service DOS function 09h directly in native 6502 code, output the string, then resume x86 execution.

This saves a considerable amount of work.

It also enables you to use native Ultimate DOS for disk operations and build your own fast keyboard and video services.

There is a tradeoff: applications that rely on undocumented DOS internals, real-mode device drivers, or unusual hardware behavior won't necessarily work. But lots of DOS software uses standard DOS and BIOS interfaces.

Your emulator must maintain guest registers such as CS, DS, ES, SS, IP, SP, BX, SI, DI and BP, calculating physical addresses while handling segment aliases and 16-bit wrapping correctly.

That part is entirely practical.

The problem is that the guest physical address might refer to anywhere in 1 MB, whereas the C64's CPU can directly access only 64 KB.

My preferred solution: REU-backed virtual RAM
Allocate perhaps 1 MB of REU space to the PC's physical address space, including video and BIOS regions as required, and use a cache in the C64's main RAM.

These are proposed engineering budgets, not measured implementation sizes. You'd need to manage ROM/I/O banking and zero-page usage carefully.

The goal is to keep enough guest code and data in ordinary C64 RAM that most emulated instructions never need to touch the REU.

Page-cache design
I'd experiment with 512-byte, 1 KB, and 2 KB pages rather than automatically selecting 4 KB.

On a guest memory access:

Calculate the 20-bit physical address.

Check whether its page is resident.

On a hit, access the corresponding C64 RAM byte.

On a miss, evict another page, writing it back if modified, and DMA the required page from REU.

Keep the instruction-fetch, stack, and currently active data pages resident whenever possible.

The design should specifically accommodate the x86 addressing modes that combine registers, such as [BX+SI+disp] and [BP+DI+disp].

It also needs to handle 16-bit values crossing page boundaries.

How expensive is an REU page fault?
A June 2026 community discussion reported approximately 4 MB/s throughput for the C64 Ultimate's REU, even with the CPU running at 64 MHz. This is a reported measurement, not a guaranteed specification, and is worth benchmarking on your own firmware.

That's a huge amount of lost CPU execution for a single cache miss.

Even 1 KB could cost the time needed to emulate dozens or hundreds of x86 instructions.

This creates an interesting tradeoff:

Small pages reduce the penalty of each miss, but large pages improve locality and simplify address translation.

I'd favor a cache that's aware of x86 segments and execution behavior, rather than a purely conventional least-recently-used cache.

For example, keep the active instruction-fetch page and likely next code page resident, plus at least one stack page and the hottest data page. Most normal 8086 programs repeatedly execute nearby code and access relatively small working sets, which you can exploit.

An optimization worth pursuing: fast segmented windows
Every normal instruction shouldn't need a complete 20-bit address translation and page-table search.

When DS or CS changes, you can recalculate a cached segment base. When IP is advancing through resident instructions, you can keep a direct C64 pointer to the cached code and only run the full translation when crossing a cache boundary.

A successful design might do something like:

CS:IP instruction fetch
    → direct cached code pointer

SS:SP stack operation
    → pinned stack cache

DS:BX ordinary data access
    → cached segment base + page lookup

B800:xxxx video write
    → specially mapped text memory
You still preserve actual x86 memory semantics; you're simply avoiding expensive translation work whenever possible.

This is where I expect some of the largest speed improvements to come from.

5. CPU emulation: difficult, but less difficult than memory
The 8086 instruction set is much more complicated than the 6502, but it's finite and well documented.

The major challenges include 16-bit arithmetic on an 8-bit CPU, ModR/M instruction decoding, effective-address calculation, conditional flags, and string instructions.

The 6502 can do 16-bit addition through pairs of 8-bit operations, so that isn't particularly problematic.

More subtle is reproducing the x86 flags exactly: carry, overflow, sign, zero, parity, auxiliary carry and direction, among others.

An optimization would be to defer calculating some flags until they're actually needed. But you'd need careful testing, since an 8086 program can inspect flags through instructions like PUSHF and conditional branches.

Especially interesting: x86 string instructions
Consider:

CLD
MOV CX, 4096
REP MOVSB
This copies 4 KB between guest memory regions.

Rather than interpreting thousands of individual x86 memory operations, you could use a native bulk-copy routine.

If the locations are in REU-backed memory, it could copy in blocks through a C64 RAM buffer using REU DMA.

It wouldn't be a direct REU-to-REU transfer through the standard REU interface, but it would avoid interpreting every individual MOVSB iteration.

This could actually outperform an original IBM PC in some memory-copying scenarios, despite the general CPU emulation overhead.

You would need correct handling for overlaps, direction flag, segment boundaries, and video-memory side effects.

6. Filesystem: this part should be quite achievable
Ultimate DOS is a particularly good fit for the project.

Its documented API already includes file open, read, write, seek, delete, rename, directory enumeration, and bulk transfers directly between files and the 16 MB REU. 

Ultimate Documentation documentation

That makes it a much better foundation than going through the 1541 emulation.

I'd implement the DOS file interface using the real-mode DOS API, particularly INT 21h, and translate filesystem requests into Ultimate DOS operations.

For example:

DOS application:
    Open C:\DATA\TEST.DAT
         ↓
INT 21h / AH=3Dh
         ↓
Native 6502 DOS layer
         ↓
Translate 8.3 filename / path
         ↓
Ultimate DOS: OPEN_FILE
And similarly for read, seek, write, close, and directory search operations.

One complication: open-file handles
The documented Ultimate DOS interface has two DOS targets with their own state, allowing two open files concurrently.

DOS applications can have considerably more file handles open.

So you can't simply map every PC DOS handle to a permanently open Ultimate DOS file.

I'd use your REU cache for file data and maintain a virtual handle table containing filenames, positions, access modes and DOS metadata. When necessary, reopen and seek on the host side, while carefully preserving pending writes and consistency.

For demanding programs, this cache could be quite beneficial.

One more advantage: you could put the bulk of an executable or its overlays directly into the REU using Ultimate DOS's LOAD_REU operation.

The loader wouldn't need to copy an entire large executable byte by byte through the 6510.

For the second option, you could implement a minimal BIOS with virtual disk sector services and boot a real DOS installation from an emulated FAT disk image. You wouldn't necessarily need to emulate an actual floppy controller if disk calls go through BIOS.

But you'd still encounter direct hardware access, timer interrupts, DOS device drivers, and programs that assume particular IBM PC hardware exists.

My preference would be to implement the native DOS-compatible approach first, then consider genuine DOS boot support as a separate compatibility mode.

A DOS application usually expects an 80×25 text screen, backed by memory beginning at:

B800:0000  Character at row 0, column 0
B800:0001  Character attribute
B800:0002  Character at row 0, column 1
B800:0003  Character attribute
You would maintain that video memory in your emulated PC's address space.

Then render it to the VIC-II's screen.

A 4×8 font means two PC characters can fit in each normal 8-pixel C64 character cell. This is an established C64 technique called Soft-80. 

C64 Soft-80

The compromises are important. Text will be small, IBM PC characters must be converted or rendered using a compressed font, and independent foreground/background colors for adjacent PC characters can't always be represented faithfully by the VIC-II.

For most text-based software, I'd initially prioritize legibility over faithful colors.

Make the screen update asynchronously from CPU execution
Don't draw pixels every time an x86 program writes to B800:xxxx.

Instead, let the program update guest video RAM and track dirty character positions or regions.

A native rendering routine would periodically convert changes into the C64 bitmap.

Likewise, intercepting BIOS video output can provide a fast path for BIOS-oriented applications.

This matters because plenty of DOS programs, including Turbo Pascal's IDE and full-screen text applications, modify video RAM directly rather than calling DOS for every character.

Would 64 MHz raster tricks help?
Potentially for particular graphics effects, but I wouldn't build the first version around them.

You've already got a tight CPU budget for the emulator. A software-driven raster effect that changes color registers continually competes directly with that budget.

The more practical approach is to support simple text rendering and perhaps CGA-compatible output, with the C64 display presenting the closest feasible representation.

For word processors, development tools and database programs, that would already be worthwhile.

I wouldn't promise 1× XT overall without measuring an actual implementation. The unknowns are too large, particularly page locality and the cost of 20-bit memory addressing.

Some workloads will perform much better than others
Text utilities and command-line tools

Likely the most successful category. They often spend much of their time doing file operations, formatted output, simple calculations and waiting for keyboard input.

You could get an experience that feels faster than an original floppy-based XT, even when raw instruction execution is slower, because file loading is so much faster.

Turbo Pascal, assemblers and compilers

These are especially interesting targets. They use substantial CPU time for tokenization, parsing, symbol tables and code generation, but don't need particularly sophisticated PC hardware.

Larger projects and compilers would stress the REU memory cache. I would expect their performance to vary significantly with source-file size and the guest's working set.

Lotus 1-2-3, dBASE and WordPerfect

Potentially compatible, but they exercise substantially more of the environment: direct video memory writes, complex keyboard behavior, file handling, memory allocation, and sometimes BIOS-specific behavior.

Even a slower-than-XT emulator could make them usefully interactive.

Games and graphics-intensive software

These would be far more problematic. Real-time graphics, PC timing assumptions, direct hardware register access, sound and joystick hardware all increase the scope.

I'd exclude them from the initial compatibility target.

9. What I would do differently for maximum performance
I'd make three architectural bets.

First: keep x86 instruction fetches cheap. A program executing a tight loop should not repeatedly calculate the full segmented address, perform a page lookup, and decode the same instruction unnecessarily. An instruction-fetch cache or compact predecoded representation could be valuable, provided cache coherence is maintained when x86 code is modified.

Second: specialize the common instruction combinations. For example, common MOV, CMP, ADD, SUB, Jcc, PUSH, and POP paths should not pass through an overly generic operand-processing framework. I'd measure execution traces from Turbo Pascal, common DOS utilities and assembly programs, then specialize the hot cases.

Third: treat bulk operations as native operations. DOS file reads into guest memory, guest video writes, large memory initialization, and repeated string instructions could all use more efficient native transfers rather than unnecessarily going through the general instruction interpreter.

There is also a fourth, more experimental approach: a tiny dynamic translator that turns frequently executed x86 basic blocks into 6502 code. That might accelerate hot loops considerably, but the very limited C64 RAM and the problem of self-modifying code make it risky. I'd try an interpreter with predecoding and fast paths before attempting that.

10. How difficult would it be with modern agentic coding?
This is a strong candidate for AI-assisted development because so much of the CPU and DOS behavior can be specified and tested deterministically.

The agent could develop and test the entire x86 interpreter on a modern computer first, then target 6502 assembly while maintaining identical behavior against a reference.

The most powerful development technique would be differential testing.

Run exactly the same short x86 programs in a well-tested reference emulator and your implementation. After each instruction, compare the CPU registers, defined flag values, memory modifications, and segment state.

That would catch an enormous number of subtle CPU bugs before you ever try running a complicated DOS application.

For performance, the agent could generate instruction-mix benchmarks, REU paging tests, and traces of real applications, then optimize the routines that account for most execution time.

I think a compelling proof of concept is a realistic project measured in weeks of focused development with good AI tooling, while a reliable implementation capable of running a broad range of real DOS software is more likely a multi-month project. Those are rough scope estimates, not measured schedules.

AI can greatly reduce the routine coding burden. It won't eliminate the need for hardware benchmarking, cycle-level optimization, and debugging 1980s compatibility quirks.

The standout opportunity is the combination of 64 MHz internal CPU/RAM execution, 16 MB of REU storage, and direct Ultimate DOS integration.

It gives you vastly more resources than anyone developing a conventional C64 PC emulator in the 1980s could have expected.

My biggest uncertainty is whether the combination of the 8086's expensive effective-address calculations and REU page faults can be reduced enough for sustained XT-class performance.

And that's also what makes this project interesting. If you can keep the hot code, stack and data resident, implement efficient direct instruction fetching, and avoid running the original DOS kernel for routine services, you have a real shot at an emulator that is not merely a curiosity, but a surprisingly usable PC/XT-class DOS environment running entirely on the C64 Ultimate.

I'd make proving that speed possible the first milestone, rather than making broad DOS compatibility the first milestone.
