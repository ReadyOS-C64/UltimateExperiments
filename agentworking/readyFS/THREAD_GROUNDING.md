## What the user actually wanted

ReadyOS file access was fragmented: most applications talked to regular IEC devices 8 or 9; the Files app listed only a limited number of entries; ReadyShell drive syntax was inconsistent; and the newer DMA loading path helped the launcher but did not unify later application file access. The user asked for a fuller **probe/laboratory application** first, so the system could be exercised and its design proven before integration into ReadyOS.

The requested shell had to expose familiar DOS operations—listing, creating, writing, appending, copying, moving, renaming, deleting, folders, media operations, metadata, and free capacity—over ordinary IEC floppies, tape where meaningful, UltimateDOS host storage, SoftwareIEC, and a future CMD/SD2IEC-style device. Cross-backend copies and whole folder trees were central, not optional polish. The design needed to distinguish an image's host filename, the mounted image/volume identity, and files *inside* that image. It needed explicit block/byte units, aliases rooted at exact locations, path-length handling, and ways to discover drives and test whether UltimateDOS and SoftIEC were active.

The user also emphasized safe previews similar to PowerShell `-WhatIf`, recursive `*`/`?`/`**` matching, include/exclude filters over a full relative stem, and a separate route for native C64 DOS wildcard selection. The console needed editable command history, pageable scrollback, a long line editor, and REU-backed working state. There was permission to use overlays if C64 RAM became tight. The other goal was to learn a coherent filesystem model that ReadyOS could eventually adopt, without making this first lab a ReadyOS app.

The user wanted extensive automated UI evidence—roughly 25–100 numbered cases, reports, and regular screenshots—and physical C64 Ultimate checks at multiple CPU speeds. A follow-up specifically required reuse of the resilient ReadyIRC/UCI Tester transaction lessons at 1, 16, and 64 MHz. Physical automation was to run in genuinely independent Terminal/background processes, and mutations were to be confined to new owned USB1/SD test folders. The user asked for durable notes so context compaction would not lose the original scope.

## Design model that emerged

### Canonical paths and identity

The public grammar is endpoint first, with `/` separators and absolute logical locations: `8:/FILE` through `30:/FILE` for IEC, `11.3:/folder/file` for a detected partition-capable IEC drive, `u:/usb1/folder/file` for UltimateDOS, `s3:/folder/file` for SoftIEC partition 3, `t:/NAME` for tape, and `@work:/suffix` for an alias fixed to an exact root. `u:/usb1/disks/demo.d81!/PROGRAM` explicitly crosses from a host image file into its contained filesystem. An alias may not escape its root through `..`. The parser's acceptance of partition syntax never itself grants partition/folder capability: the detected drive profile must authorize each operation.

This scheme deliberately avoids C64 OS's filename-before-path form. Every operation resolves to a normalized absolute logical path; a backend's mutable current directory is reestablished per transaction rather than trusted as shell state. Display spelling, exact UCI/IEC access spelling, decoded host filename, C64 file type, image/volume label, contained filename, and size units must stay separate. Physical firmware 3.14 evidence eventually proved an exact lowercase host image `disk1.d81` with 819,200 host bytes, independently of its mounted `RFMEDIA1` volume and 3,160 C64 blocks. SoftIEC capacity was shown as `FREE UNAVAILABLE` when the backend could not give an honest value.

Shell globs (`*`, `?`, `**`) and whole-relative-stem `--include`/`--exclude` filters are client-side. `--native-pattern` is a distinct read-only backend selection step. For mutation, ReadyFS enumerates and freezes exact names and types in a bounded REU plan, shows the complete plan, and uses only exact-name actions. `--whatif`/`--dry-run` makes no mutation. Applying a native-selected action requires explicit `--apply`; `--yes` or `--force` alone cannot authorize a wildcard mutation. A plan that truncates at its entry limit or contains an unsupported REL entry is rejected as a whole. It never sends wildcard scratch/write/rename to a device.

### Capabilities instead of drive-number guesses

An IEC device is probed through resident-owned command-channel I/O and classified into a per-drive capability profile cached in REU. The cache checks both record marker and device number, so a status from one drive cannot authorize another. CMD/SD2IEC translations are allowed only for a profile advertising the relevant partition, folder, and image capabilities. An ordinary VICE 1581 is intentionally used to show denial or bounded failure after a synthetic ReadyFS capability record is injected; this proves the dispatcher, not a real SD2IEC. IDE64, discussed in a related analysis thread, is a different high-level KERNAL/expansion-port backend and cannot stand in for physical SD2IEC IEC timing, partition syntax, or disk-image semantics.

The CMD/SD2IEC translator knows native forms such as partition-qualified opens, `$` directories, `S` scratch, `MD`/`RD`, `R new=old`, image `CD`, and unmount/back-arrow commands. It preflights component/path/command lengths. Image-contained `!` paths that require an unproven hidden mount/restore transaction are rejected rather than silently treated as regular folders.

### Memory and execution architecture

The first PRG was monolithic; memory forced a resident shell/I/O kernel plus a shared `$B600–$C5FF` execution window and REU-cached 4 KiB sidecars. A monolithic PRG was retained for direct physical C64U runs, and an overlay D81 carries the long-term shell architecture. The current build has **12 sidecars** for matching, planning/execution, help/journal, backend composition, CMD paths, drive profiling, utility/history, tree control, content, batch/editor, recursive names/control, and tape/policy. Resident code ends at `$B5A3`: only **8 bytes** remain before the stricter `$B5AC` KERNAL scratch ceiling. The monolithic image ends at `$C4EB`, below `$C600`. Many sidecars are close to 4 KiB. Memory pressure is a continuing architectural constraint, not a cosmetic build issue.

The crucial execution pattern is: a sidecar plans/yields one exact action; resident code restores safe code and performs KERNAL IEC or UCI I/O; the result is written to RFJ1; only then is the pending executor action acknowledged. The overlay must not make a device call or hold a return address/pointer into bytes that a sidecar swap may overwrite. Recursive traversal uses a cooperative, bounded, stackless queue/checkpoint in REU, not a deep cc65 call stack. The REU also holds aliases, profiles, history, 24 scroll pages, config rollback/staging, immutable recursive roots, action plans, RFJ1 journal, and a separate 16 KiB batch-script area. The current exact map and nonoverlap checks are in the generated build report.

Several difficult cc65 failures shaped this design. Multi-argument nested C calls across overlays/REU DMA lost arguments and initially collapsed sidecar cache stores into slot zero. The fix was static request records, one-pointer gateways, and flat assembly REU store/fetch routines with explicit cc65 argument cleanup. Deep local variables also collided with software-stack/memory ceilings. BSS and zero-page runtime boundaries matter. Source-shape verifiers now guard overlay DMA, pipeline ordering, UCI protocol, linker limits, and REU disjointness. A green host-only composition test never substituted for a C64 call through fetch/dispatch/restore.

### UCI and physical firmware lessons

UCI is an asynchronous state machine. ReadyFS synchronizes to fully quiet IDLE, writes the entire command, PUSHes once, waits for DATA_LAST/MORE, drains both data and status queues, accepts a block only after both are empty, observes the MORE→BUSY transition, and waits for final quiet IDLE. ABORT is also asynchronous and serviced to quiescence. Poll counts are failure bounds, not delays. At 64 MHz, a six-byte directory MORE block exposed a transition too brief to see across normal C overhead, so a small adjacent assembly DATA_ACC/transition observer was introduced while C retained queue draining and recovery. A one-command `READ_DIR` can stream many entry blocks. Physical tests at 1/16/64 MHz, including abort/recovery/re-identify, are recorded; VICE is not counted as UCI hardware proof.

Firmware 3.14 required several adaptations. SoftIEC IDENTIFY returned legacy ASCII `00,OK` rather than the newer binary success encoding. FTP exposed roots `USB1` and `SD`, while SoftIEC's internal configuration could use `/USB0/`; public aliases and raw backend paths cannot be conflated. UltimateDOS `FILE_STAT` could say file-not-found for a real long host path; parent `READ_DIR` exact-leaf lookup followed by `OPEN_FILE`/`FILE_INFO` was more reliable. The UltimateDOS FTP/SEQ bridge uppercased text and changed line endings, so SEQ host FTP round trips do not prove binary fidelity; PRG/CRC or independent byte reads were used for that claim. PETSCII uppercase/underscore and command-prefix translation required explicit handling.

SoftIEC firmware 3.14's BASIC directory stream was not an exhaustive FAT enumeration oracle and could omit later entries. Explicit SEQ/PRG/USR opens plus checked DOS status became the safer existence/type route. A generic REL existence probe was found unsafe because the firmware may create a missing `.rel`; it is forbidden. A target-5 close call and its exact ordering relative to KERNAL close and DOS-status read were needed because UCI and IEC status shared scratch. `CD:` is performed component by component with a checked status, and a virtual-root `/`→`USB1` bridge was physically established. Crowded parent directories produced visibility/`CD:` limits, so shallow, uncrowded SoftIEC-visible roots are a practical test and integration boundary.

3. **August 15–16: planner, journal, and overlay ABI.** Recursive planning and stackless walking were developed. The project added RFJ1 variable-length operation records and RFA1 action completion reports, then made the C64 overlay gateway real. After the one-pointer/assembly boundary was fixed, VICE proved a real resident IEC action, journal-before-ACK, overlay restore, and a converted REU journal report.
4. **August 16: CMD profiles, recursion, native patterns.** CMD/SD2IEC path translation and per-drive capability gates were added. Cooperative IEC batches became real: cross-device copies, recursive copy/move/delete, full-stem filters, stop/continue policies, and failed-action RFJ1 reports. Discovery scanned IEC 8–30 with bounded LISTEN handling; D64/D71/D81 capacity and large directories were reported/paged. Native-pattern read-only selection, exact-name WhatIf, explicit apply, whole-plan rejection, type gate, and byte-preserving postconditions passed VICE.
5. **August 16–17: broad command surface.** Additional sidecars carried history, a cooperative tree controller, content views (`type`/`head`/bounded `tail`), streaming CRC-32, versioned built-in `test`, disposable IEC `format`, and `run` scripts. Every original command token was ultimately dispatched, though not every backend/typed-result path was finished. `run` reads a SEQ script into a dedicated 16 KiB REU area and closes the file before dispatch. It supports comments, `ONERROR STOP|CONTINUE`, and `EXPECT RC N`, rejects nested `RUN`, and forbids interactive prompts. `EXPECT RC` currently parses only one digit, while the result ABI defines 0–11; some older I/O/verify/partial/internal handlers still need typed-result conversion.
6. **August 17–18: hardware integration and media.** Physical UCI recovery passed at 1/16/64 MHz. A 4,069-byte IEC↔UltimateDOS PRG round trip preserved bytes/type and restored Drive A. Flat and nested UltimateDOS→SoftIEC work progressed through several fail-closed diagnostics to a physically proven directory plus three-file recursive copy, independently read back afterward. A nested `**/inside` WhatIf selected one leaf and proved zero mutation through directory/CRC/owner/drive oracles. Physical Ultimate mount/swap/dismount and exact Drive A restoration passed. Lowercase host image name, exact host bytes, internal image volume, and C64 blocks were separately proven. Named sequential disk→tape and tape→disk transfers passed with disposable VICE TAP media; unsupported tape random access/tree operations are explicitly refused.
7. **August 17–20: remaining boundaries and relocation.** SoftIEC→UltimateDOS reverse tree source was implemented and host/VICE checked, but physical proof was blocked by C64U configuration/`run_prg`/sidecar launch failures *before* a successful owner-gated copy. CMD/SD2IEC tree routing was VICE-proven through a synthetic capability profile, with bounded failure on an ordinary 1581. The original thread then moved all ReadyFS material to this standalone directory, replaced ReadyOS release-image dependencies in REL tests with generated fixtures, forced a full rebuild, compiled all 35 VICE plans, passed fresh smoke/REL suites, and passed a five-case **read-only** physical suite from the relocated PRG at 64 MHz. The original thread's subsequent work focused on ReadyOS rather than advancing ReadyFS.

The batch language is deliberately small. A real success fixture runs `PWD`, asserts `EXPECT RC 0`, runs `MATCH "*" "ABC"`, and asserts another zero. A continue fixture runs an unknown `BOGUS` command, checks result 1, then proves `PWD` still runs. A typed fixture checks result 4 for invalid `NEW`, 5 for a missing deletion target, and 6 for a file conflict. A script attempting a guarded overwrite without `--yes` returns interaction result 3 and leaves the original bytes unchanged. The stable result header reserves 0 success, 1 unknown, 2 unavailable, 3 interaction, 4 usage, 5 not found, 6 conflict, 7 unsupported, 8 I/O, 9 verification, 10 partial, and 11 internal. `RUN` is an experiment/replay and assertion facility, not a variable/loop/branching language. Its `RUN DONE` command count differs from the recursive executor's `BATCH DONE` action count.

## Safety and evidence interpretation

Physical mutation suites may act only below a new `/usb1/READYFS_TEST/<run-id>` or `/sdcard/READYFS_TEST/<run-id>` with an exact matching ownership marker. Both normalized prefix and marker bytes must be checked before each destructive step; aliases, image boundaries, or `..` cannot escape. Roots, failed diagnostics, and logs are preserved by default. Configuration and drive state must be captured and restored exactly, including failure paths. A deliberate post-configuration failure test ended with nonzero status but proved exact settings/Drive A restoration. A run stopped before marker admission is not application or filesystem proof.

C64U REST/FTP calls from Codex require a genuinely Terminal-owned/background bash; foreground one-shot calls can falsely report no route or reset. An early preflight was invalidated because failed/empty FTP captures had been treated as success; later scripts use strict shell failure and nonempty checks. REST success alone never authorizes mutation if the exact marker cannot be fetched. C64U REST RAM reads during active disk loading can disturb loading, so visual completion should precede memory inspection. The relocated read-only UI test uses bounded `u:/SD` directory enumeration because an ever-growing USB1 root defeated a fixed timeout without implying a code relocation failure.

Separate **implemented**, **host-tested**, **VICE-tested**, and **physical-hardware-proven** claims. A synthetic SD2IEC profile plus an ordinary 1581 proves ReadyFS admission and translation but not successful SD2IEC commands. SoftIEC status `$01` for unsupported map is a target result, not UCI transport failure. Failed retries that occurred before launch/owner admission do not disprove reverse-tree logic. Conversely, 58/60 UI cases do not close the broader scope audit. Preserve raw historical manifests, including failed runs and old absolute paths, as provenance rather than rewriting them to look current.
