Target-Tested SQL Examples

These statements are executed by the compiled 6510 test program in both Peddle REU sizes and by the automated VICE D81/1581 lane. This is an evidence list, not a claim that the rest of the planned dialect is already implemented.

How to use this evidence catalog

The statements below keep their fixture names and expected results. They are executable test cases, including deliberate rejections—not a single script to paste into a fresh shell. Some statements exceed the shell's 160-byte line limit and are submitted through the engine API.

For a first pass, start with schema and types, three-source scans, nested predicates, or the sales benchmark. The chapter headings group the full original catalog without dropping any SQL or assertions.

Schemas, values and basic queries

Performance: some advanced queries are very slow right now.

Joins, correlated subqueries, grouping, sorting and duplicate elimination can walk the same relationships repeatedly. For demanding work, it is often faster to filter/project into TEMP tables, index the useful intermediate columns, and run the next query against that smaller result. The tested seven-step sales pipeline took 425.88 seconds PAL, compared with 2,300.2 seconds for the original grouped join—about 5.4× faster, including its intermediate table and index builds. These are measurements of this fixture, not a guarantee for every query.

Why this happens and how to stage a query.

Schema and physical types

create table sqltypes (
  flag boolean not null,
  tiny i8,
  small i16 null,
  wide i32,
  huge i64,
  money fixed8_8,
  value float,
  label char(9)
);

The test reopens the catalog and checks all eight columns, the 33-byte physical row width (including its null bitmap), the nullable I16, and CHAR(9).

CREATE TABLE SQLVAR (BODY TEXT NULL, RAW BLOB)

This verifies variable-value columns occupy stable four-byte handles in the fixed row.

INSERT INTO SQLVAR VALUES ('C64 ''TEXT''', X'00FF104142');
INSERT INTO SQLVAR VALUES (NULL, X'');

The first statement verifies escaped TEXT plus a binary literal containing a zero byte. The second verifies nullable TEXT and a zero-length BLOB. The target checks handle placement, heap kind and length, exact payload bytes, and row counts.

CREATE TABLE SQLDML (
  ID I16,
  NAME CHAR(8),
  ACTIVE BOOLEAN,
  SCORE I32 NULL
)

Inserts and literal encoding

INSERT INTO SQLDML VALUES (42, 'ADA', TRUE, NULL)

The test scans the stored row, checks the null bit for SCORE, little-endian I16, space padding for CHAR(8), and the boolean byte.

insert into sqldml values (-7, 'O''NEIL', false, 123456);

This covers case-insensitive keywords/names, a negative integer, doubled-quote escaping, false, a four-byte integer, and an optional trailing semicolon. The row iterator must return both inserts in deterministic physical order and then RSQL_ERR_NOT_FOUND.

Named enumerations

CREATE TYPE MOOD AS ENUM8 (SAD = 1, OK = 2, HAPPY = 7);
CREATE TYPE BIGCODE AS ENUM16 (LOW = 1, HIGH = 300);
CREATE TABLE EDATA (ID I16, STATE MOOD, CODE BIGCODE NULL);

INSERT INTO EDATA VALUES (1, MOOD.HAPPY, BIGCODE.HIGH);
INSERT INTO EDATA VALUES (2, MOOD.SAD, NULL);
SELECT COUNT(*) FROM EDATA WHERE STATE = MOOD.HAPPY;
SELECT STATE, CODE FROM EDATA WHERE ID = 1;
UPDATE EDATA
SET STATE = MOOD.OK, CODE = BIGCODE.LOW
WHERE STATE = MOOD.HAPPY;

The target verifies enum widths, member values, table-column catalog IDs, nullable metadata, one-byte and two-byte physical values, qualified filtering, typed cursor results, and qualified fixed-record UPDATE. It also rejects an unknown named column type, duplicate enum values, an ENUM8 member above 255, missing members, a qualifier for the wrong enum, an enum literal assigned to a non-enum column, and numeric values outside ENUM8/ENUM16 unsigned ranges.

SELECT and cursor results

SELECT BODY, RAW FROM SQLVAR;
SELECT COUNT(BODY) FROM SQLVAR;

The cursor reports logical TEXT/BLOB payload lengths rather than the four-byte physical handle width. rsql_value_read() streams the full TEXT and a BLOB slice, including zero bytes. The second row returns NULL TEXT and a non-NULL, zero-length BLOB; COUNT(BODY) returns one.

SELECT COUNT(*) FROM SQLDML

Opened through the query/cursor ABI. It returns one non-NULL I64 value equal to two, then reaches end-of-cursor. Closing it makes a later next call return RSQL_ERR_CURSOR_STATE.

select name, score, id from sqldml;

The cursor returns both rows in physical order. Tests check projection order, the first row's NULL SCORE, the second row's 123456, both IDs, and streamed eight-byte CHAR values through rsql_value_read().

SELECT COUNT(*) FROM SQLDML WHERE SCORE IS NOT NULL

This verifies NULL-aware filtering happens before aggregation: only the second row contributes, so the result is one.

SELECT ID FROM SQLDML WHERE ID < 0

This exercises signed, width-aware integer comparison. It returns only -7 and then end-of-cursor.

Compound predicates and LIKE

SELECT COUNT(*)
FROM SQLDML
WHERE ID < 0 OR ACTIVE = TRUE AND SCORE IS NULL

Returns two and proves AND binds more tightly than OR.

SELECT COUNT(*)
FROM SQLDML
WHERE (ID < 0 OR ACTIVE = TRUE) AND SCORE IS NULL

Returns one, proving parentheses override precedence.

SELECT COUNT(*)
FROM SQLDML
WHERE NOT (SCORE = NULL) OR ID < 0

Returns one. Comparisons with NULL produce UNKNOWN, NOT preserves UNKNOWN, and UNKNOWN OR TRUE becomes TRUE only for the negative-ID row.

SELECT COUNT(*)
FROM SQLDML
WHERE NAME LIKE 'a_a%' OR NAME LIKE '%NEIL'

Returns two and covers folded matching, _, %, suffix matching, and trimming of fixed-CHAR padding for LIKE.

SELECT COUNT(*) FROM SQLDML WHERE NAME NOT LIKE '%NEIL'

Returns one and verifies the standard infix NOT LIKE spelling.

SELECT COUNT(*)
FROM SQLDML
WHERE ID >= -7 AND ID <= 42 AND ID != 0
  AND ID <> 99 AND ID > -8 AND ID = 42

Returns one while executing every supported comparison spelling in one bounded postfix predicate program.

Grouping and aggregates

The aggregate lane creates a data set with duplicate keys, negative values, and NULL-only groups:

CREATE TABLE AGGDATA (REGION CHAR(4), AMOUNT I16 NULL);
INSERT INTO AGGDATA VALUES ('N', 10);
INSERT INTO AGGDATA VALUES ('N', 20);
INSERT INTO AGGDATA VALUES ('S', -5);
INSERT INTO AGGDATA VALUES ('S', NULL);
INSERT INTO AGGDATA VALUES ('E', NULL);
INSERT INTO AGGDATA VALUES ('N', 10);
SELECT DISTINCT COUNT(*), COUNT(AMOUNT), SUM(AMOUNT), AVG(AMOUNT),
       MIN(AMOUNT), MAX(AMOUNT)
FROM AGGDATA
ORDER BY 3 DESC

The result is 6, 4, 35, 8, -5, 20. COUNT(AMOUNT) ignores NULL and the current integer AVG truncates toward zero into I64.

SELECT DISTINCT REGION, COUNT(*), COUNT(AMOUNT), SUM(AMOUNT), AVG(AMOUNT),
       MIN(AMOUNT), MAX(AMOUNT)
FROM AGGDATA
GROUP BY REGION
ORDER BY 4 DESC

The target checks all three groups. N gives 3, 3, 40, 13, 10, 20; S gives 2, 1, -5, -5, -5, -5; and NULL-only E returns NULL for SUM, AVG, MIN, and MAX.

SELECT REGION, SUM(AMOUNT)
FROM AGGDATA
WHERE AMOUNT IS NOT NULL
GROUP BY REGION
ORDER BY REGION DESC

This proves WHERE is applied before grouping, excludes the NULL-only E group, and orders named group keys directly; results are S then N.

SELECT REGION, AMOUNT, COUNT(*)
FROM AGGDATA
GROUP BY REGION, AMOUNT

This verifies compound grouping keys, NULL key equality, and duplicate ('N', 10) collapse.

SELECT COUNT(*), COUNT(AMOUNT), SUM(AMOUNT), AVG(AMOUNT),
       MIN(AMOUNT), MAX(AMOUNT)
FROM EMPTYDATA

The empty-table result is one row containing 0, 0, NULL, NULL, NULL, NULL.

Commodore FLOAT

CREATE TABLE FLOATDATA (REGION CHAR(2), VALUE FLOAT NULL);
INSERT INTO FLOATDATA VALUES ('A', 1.5);
INSERT INTO FLOATDATA VALUES ('A', 2.25);
INSERT INTO FLOATDATA VALUES ('B', -0.75);
INSERT INTO FLOATDATA VALUES ('B', NULL);
INSERT INTO FLOATDATA VALUES ('A', 2);

SELECT VALUE FROM FLOATDATA;
SELECT VALUE FROM FLOATDATA WHERE VALUE >= 1.5 AND VALUE < 2.25;
UPDATE FLOATDATA SET VALUE = 3.5 WHERE VALUE = -0.75;

SELECT COUNT(*), COUNT(VALUE), SUM(VALUE), AVG(VALUE),
       MIN(VALUE), MAX(VALUE)
FROM FLOATDATA;

SELECT REGION, COUNT(VALUE), SUM(VALUE), MIN(VALUE), MAX(VALUE)
FROM FLOATDATA
GROUP BY REGION
ORDER BY 3 DESC;

The target verifies exact Commodore five-byte encodings for positive, negative, integer-coerced, updated, and aggregate values. The ungrouped row is 5, 4, 5.0, 1.25, -0.75, 2.25; group A returns count 3, sum 5.75, min 1.5, max 2.25; group B ignores its NULL and returns -0.75 for sum, min, and max. rsql_value_read() and inline cursor bytes must agree exactly.

Aggregate/grouped shaping is also combined with pagination:

SELECT REGION, COUNT(*)
FROM AGGDATA
GROUP BY REGION
ORDER BY 2 DESC
LIMIT 1 OFFSET 1;

Group counts are N=3, S=2, and E=1, so the selected row is S,2. Ungrouped DISTINCT is a one-row proof; grouped DISTINCT is optimized away when every group key is projected. Exact projected-tuple elimination is tested when a key is omitted:

SELECT DISTINCT REGION
FROM AGGDATA
GROUP BY REGION, AMOUNT;

The compound groups are (N,10), (N,20), (S,-5), (S,NULL), and (E,NULL), but the projected result is exactly N, S, E. This proves deduplication across different group identities without a materialized set.

UPDATE AGGDATA SET AMOUNT = 1.5 WHERE REGION = 'N';

Rejected with RSQL_ERR_TYPE_MISMATCH: a decimal FLOAT literal is not silently narrowed into I16.

Transactions and indexed access

Atomic mutation failure injection

CREATE TABLE JFAIL (ID I16)
INSERT INTO JFAIL VALUES (1)
INSERT INTO JFAIL VALUES (2)
SELECT COUNT(*) FROM JFAIL

The target injects I/O failure before every canonical write in CREATE and in both INSERT paths. After each failure, the table/row count is unchanged and the same first free REU page remains available. The non-injected statements then commit normally and the final count is two.

The variable-value lane repeats this for a two-handle TEXT/BLOB insert. It uses the committed transaction's measured write count to inject failure at every write boundary, proving that payload pages, directory entries, handle counters, the row, and allocation bitmap roll back together.

DELETE

DELETE FROM JFAIL WHERE ID = 1;
DELETE FROM JFAIL WHERE ID > 100;
DELETE FROM JFAIL WHERE ID = 2 OR ID = 99;
DELETE FROM JFAIL;

The tests verify affected-row counts of one, zero, one, and two, along with COUNT(*) after each statement. Failure is injected before both writes of a single-row delete and all four writes of a two-row delete; every failure leaves both rows and the allocation state intact before a successful retry.

Variable ownership is exercised separately:

DELETE FROM VDEL WHERE BODY IS NULL;
DELETE FROM VDEL;
DELETE FROM VFAIL;

The filtered statement tombstones the empty BLOB handle but leaves the other row's TEXT/BLOB active. The following statement tombstones those two handles, and explicit compaction reclaims exactly two payload pages. A two-row VFAIL statement owns four nonempty handles; failure injection at every measured write boundary restores both rows and all four active directory entries. The commit tombstones all four and compaction reclaims four pages.

UPDATE

UPDATE UDATA
SET NAME = 'Z', SCORE = 99
WHERE ID >= 2 AND ID < 3;

UPDATE UDATA
SET SCORE = NULL, NAME = 'N'
WHERE ID >= 2;

UPDATE UDATA SET SCORE = 7 WHERE ID > 99;

The tests verify affected counts of one, two, and zero; multiple assignments; compound filtering; CHAR padding; and transitions to NULL. Follow-up COUNT queries verify the updated predicates. A two-row UPDATE is replayed with failure before each row-page write; both rows retain their old values and the allocation state until the successful retry.

Variable ownership is covered in a fifth target lane:

UPDATE VUP
SET BODY = 'REPLACED', RAW = X'AA00', NAME = 'Z'
WHERE ID = 1;

UPDATE VUP SET BODY = 'BOTH', RAW = X'FF' WHERE ID <= 2;
UPDATE VUP SET BODY = NULL, RAW = NULL WHERE ID = 2;
UPDATE VUP SET BODY = 'BORN', RAW = X'' WHERE ID = 3;
UPDATE VUP SET BODY = 'NEVER', RAW = X'99' WHERE ID > 99;

The target proves each matching row receives different handles even when the literal payload is identical, old handles become tombstones, payload bytes and zero-length BLOBs remain exact, fixed and variable assignments commit together, NULL transitions work in both directions, and a no-match update allocates nothing. A two-row TEXT/BLOB/fixed update is then retried with failure before every dynamically measured canonical write; every failure restores rows, old handles, predicates, and the first-free page. The committed retry tombstones four old handles, and compaction reclaims exactly four payload pages.

Persistent named indexes

The storage lane builds both compound and single-column indexes:

CREATE TABLE IDXT (ID I16, NAME CHAR(64), NOTE TEXT NULL);
INSERT INTO IDXT VALUES (42, 'ADA', NULL);
INSERT INTO IDXT VALUES (-7, 'O''NEIL', 'TEXT');

CREATE INDEX IDX_NAME_ID ON IDXT (NAME, ID);
CREATE INDEX IDX_ID ON IDXT (ID);

Queries opt in by index name and still apply the complete WHERE predicate:

SELECT ID
FROM IDXT USING INDEX IDX_NAME_ID
WHERE NAME = 'O''NEIL';

SELECT ID
FROM IDXT USING INDEX IDX_ID
WHERE ID = 42;

The target checks the persisted descriptor and first leaf, then exercises index maintenance through all three DML operations:

UPDATE IDXT SET NAME = 'GRACE' WHERE ID = 42;
SELECT ID FROM IDXT USING INDEX IDX_NAME_ID WHERE NAME = 'GRACE';

INSERT INTO IDXT VALUES (5, 'BOB', NULL);
INSERT INTO IDXT VALUES (6, 'ZED', NULL);
SELECT ID FROM IDXT USING INDEX IDX_NAME_ID WHERE NAME = 'ZED';

DELETE FROM IDXT WHERE ID = -7;
SELECT ID FROM IDXT USING INDEX IDX_NAME_ID WHERE NAME = 'O''NEIL';

The 64-byte CHAR component deliberately gives the compound leaf a capacity of three, so the fourth row proves leaf splitting and linked-leaf traversal. A shutdown/reinitialize between insertion and deletion proves index persistence. The UPDATE is replayed with failure at every measured journal write; every failure restores both the row and both indexes, while the successful retry makes only the new key visible.

CREATE INDEX IDX_NOTE ON IDXT (NOTE);
SELECT ID FROM IDXT USING INDEX NO_SUCH_INDEX;
SELECT NAME FROM PEOPLE USING INDEX IDX_NAME_ID;

These respectively reject a variable-width key, a missing name, and an index owned by a different table. Creating IDX_NAME_ID twice is also rejected.

Joins, subqueries and result shaping

Two-source joins

The join lane creates customers and orders with duplicate matches, unmatched rows, a NULL foreign key, signed values, TEXT, and a shared named enum:

CREATE TYPE STATE AS ENUM8 (ACTIVE=1, INACTIVE=2);
CREATE TABLE CUST (
    ID I16, NAME CHAR(8), STATE STATE, LIMITV FIXED8_8
);
CREATE TABLE ORDR (
    ID I16, CID I32 NULL, TOTAL I16,
    LABEL CHAR(8), NOTE TEXT NULL, STATUS STATE, AMOUNT FIXED8_8
);

An INNER JOIN exercises cross-width signed equality, compound post-join WHERE, LIKE, duplicate inner matches, and TEXT streaming:

SELECT C.NAME, O.ID, O.NOTE
FROM CUST AS C
INNER JOIN ORDR AS O ON C.ID = O.CID
WHERE O.TOTAL >= 50 AND C.NAME LIKE 'A%';

The target receives (ADA,10,'FIRST') and (ADA,11,NULL) in deterministic outer/inner physical order and reads FIRST through rsql_value_read().

LEFT JOIN verifies both NULL extension and the distinction between ON and WHERE:

SELECT C.ID, O.ID
FROM CUST AS C
LEFT OUTER JOIN ORDR AS O ON C.ID = O.CID;

SELECT C.ID
FROM CUST AS C
LEFT JOIN ORDR AS O ON C.ID = O.CID
WHERE O.ID IS NULL;

SELECT C.ID, O.ID
FROM CUST AS C
LEFT JOIN ORDR AS O
  ON C.ID = O.CID AND O.TOTAL > 0;

The first returns (1,10), (1,11), (2,12), and (3,NULL). The second returns only customer 3. In the third, customer 2 is NULL-extended because its only order fails ON, while customer 3 remains unmatched; the result has four rows.

CROSS JOIN applies column references and literals in WHERE:

SELECT C.ID, O.ID
FROM CUST AS C CROSS JOIN ORDR AS O
WHERE C.ID = O.CID;

It returns three matching pairs. A separate CROSS query checks literal filters, and empty-inner tests prove LEFT returns all three outer rows while CROSS returns none.

CHAR and enum column references are first-class:

SELECT C.ID, O.ID
FROM CUST AS C JOIN ORDR AS O ON C.NAME = O.LABEL;

SELECT C.ID, O.ID
FROM CUST AS C JOIN ORDR AS O
  ON C.STATE = O.STATUS AND C.ID = O.CID
WHERE C.STATE = STATE.ACTIVE;

The target also rejects ambiguous unqualified ID, incompatible CHAR = I16, and a self-join without distinct aliases.

FIXED8_8 uses its native two-byte representation for column references and scales an integer literal before comparison. The same predicate now forces exact joined scalar DISTINCT across different inner row identities:

SELECT DISTINCT LENGTH(C.NAME)
FROM CUST AS C JOIN ORDR AS O ON C.LIMITV = O.AMOUNT
WHERE O.AMOUNT >= 2;

Four joined pairs qualify: two expose ADA and two expose CY, so the virtual LENGTH values are 3,3,2,2. The target verifies exactly two result rows, proving fixed-point predicate comparison and scalar duplicate elimination across different joined pairs.

Joined ORDER BY remains a bounded nested-loop producer rather than a materialized result:

SELECT O.ID
FROM CUST AS C
JOIN ORDR AS O ON C.ID = O.CID
ORDER BY O.TOTAL ASC, O.ID DESC;

The target returns order IDs 12, 10, 11, proving inner-source keys, multi-key direction, and deterministic selection. Pagination composes with the ordered stream:

SELECT O.ID
FROM CUST AS C
JOIN ORDR AS O ON C.ID = O.CID
ORDER BY O.TOTAL ASC, O.ID DESC
LIMIT 2 OFFSET 1;

This returns 10, 11. LEFT-null ordering is checked independently:

SELECT C.ID
FROM CUST AS C
LEFT JOIN ORDR AS O ON C.ID = O.CID
ORDER BY O.ID DESC;

It returns customer IDs 2, 1, 1, 3; the NULL-extended customer is last for DESC. These cases retain only outer/inner row IDs and a NULL-extension flag. They do not allocate joined rows or an execution plan.

Joined fixed scalar projections also drive the selection comparator directly:

SELECT LENGTH(C.NAME), SUBSTR(O.LABEL,2,2), C.NAME||O.LABEL
FROM CUST AS C
JOIN ORDR AS O ON C.ID=O.CID
ORDER BY 3;

The ordered concatenations are ADAADA, ADABAG, and BOBBAD. The first row is checked as 3,'DA','ADAADA', and the harness consumes all three rows. This exercises LENGTH, substring, source-to-source concatenation, a projection ordinal, and repeated target-row reads without a scalar result buffer.

Joined grouping and aggregates

The dedicated joined-aggregate lane widens the order fixture with signed I8, I32, I64, nullable FLOAT, and an empty inner table. It first verifies complete ungrouped accumulation over an INNER producer:

SELECT COUNT(*), COUNT(O.TOTAL), SUM(O.TOTAL), AVG(O.TOTAL),
       MIN(O.TOTAL), MAX(O.TOTAL), SUM(C.ID)
FROM CUST AS C
JOIN ORDR AS O ON C.ID = O.CID;

The row is 3,3,120,40,-5,75,4. Separate queries verify I8 values -100,100,7, I32 values 100000,-30000,-70000, I64 values including 4294967296, and exact Commodore FLOAT values 1.5,2.25,-0.75. The I64 sum is 4294967300; FLOAT sum/average/min/max are 3,1,-0.75,2.25.

LEFT and empty-input semantics are explicit:

SELECT C.ID, COUNT(*), COUNT(O.ID), SUM(O.TOTAL)
FROM CUST AS C LEFT JOIN ORDR AS O ON C.ID = O.CID
GROUP BY C.ID;

SELECT COUNT(*), SUM(E.ID)
FROM CUST AS C CROSS JOIN EMPTYJ AS E;

Customer 3's NULL-extended group is 3,1,0,NULL; the empty ungrouped result is the required single row 0,NULL. WHERE-before-grouping is checked with O.TOTAL >= 0.

Nullable inner and compound outer/inner keys are discovered through bounded first-pair rescans:

SELECT O.CID, COUNT(*)
FROM CUST AS C CROSS JOIN ORDR AS O
GROUP BY O.CID;

SELECT C.ID, O.CID, COUNT(*)
FROM CUST AS C CROSS JOIN ORDR AS O
GROUP BY C.ID, O.CID
LIMIT 1 OFFSET 5;

The first emits physical-first groups (1,6),(2,3),(NULL,3),(99,3); the second proves compound grouping and pagination with (2,2,1).

Joined grouped shaping covers named inner keys, aggregate ordinals, FLOAT, exact DISTINCT, two-key ordering, and pagination:

SELECT C.ID, COUNT(*), SUM(O.TOTAL)
FROM CUST AS C JOIN ORDR AS O ON C.ID = O.CID
GROUP BY C.ID ORDER BY 3 DESC;

SELECT O.CID, COUNT(*)
FROM CUST AS C CROSS JOIN ORDR AS O
GROUP BY O.CID ORDER BY O.CID DESC;

SELECT DISTINCT C.ID
FROM CUST AS C JOIN ORDR AS O ON C.ID = O.CID
GROUP BY C.ID, O.TOTAL ORDER BY C.ID DESC;

SELECT DISTINCT COUNT(*)
FROM CUST AS C JOIN ORDR AS O ON C.ID = O.CID
GROUP BY C.ID ORDER BY 1 DESC;

The first returns customer 1 before 2 (125 > -5); the second places the nullable inner key last under DESC; the third collapses three groups to IDs 2,1; and the fourth compares aggregate-only projected tuples and returns counts 2,1. An ordered compound query with LIMIT 1 OFFSET 1 returns (1,50,1). Ungrouped ordered and ordered-empty aggregate queries remain one-row results.

Correlated scalar, IN, and EXISTS subqueries

The join lane also exercises the complex-query sidecar as a correlated subquery executor. EXISTS and NOT EXISTS use both accepted projection forms:

SELECT C.ID FROM CUST AS C
WHERE EXISTS (
  SELECT 1 FROM ORDR AS O WHERE O.CID=C.ID
);

SELECT C.ID FROM CUST AS C
WHERE NOT EXISTS (
  SELECT * FROM ORDR AS O WHERE O.CID=C.ID
);

These return (1,2) and (3) respectively. A self-correlated query with distinct C and X aliases returns all three customers; reusing the same alias is rejected.

The outer correlated producer also supports bounded ordering:

SELECT C.ID FROM CUST AS C
WHERE EXISTS (
  SELECT 1 FROM ORDR AS O WHERE O.CID=C.ID
)
ORDER BY 1 DESC;

SELECT C.ID FROM CUST AS C
WHERE EXISTS (
  SELECT 1 FROM ORDR AS O WHERE O.CID=C.ID
)
ORDER BY C.ID DESC
LIMIT 1 OFFSET 1;

The first returns 2,1; the second returns 1. Together they prove a raw projection ordinal, a named qualified outer key, descending selection, and ordered pagination without materializing the correlated result.

Exact correlated DISTINCT uses an empty inner table to make all outer rows eligible while projecting a duplicate virtual scalar:

SELECT DISTINCT LENGTH(NAME)
FROM CUST AS C
WHERE NOT EXISTS (
  SELECT 1 FROM EMPTYJ AS E WHERE E.ID=C.ID
);

The three outer values are 3,3,2; the cursor returns exactly two rows. This verifies complete fixed scalar comparison across prior matching correlated results.

The same correlated producer orders multiple fixed scalar forms:

SELECT DISTINCT LENGTH('ABC'), SUBSTR('WXYZ',2,2), C.NAME||'X'
FROM CUST AS C
WHERE EXISTS (
  SELECT 1 FROM ORDR AS O
  WHERE O.CID=C.ID AND O.ID>=10 AND O.TOTAL>-10
)
ORDER BY 3;

The rows are ordered by ADAX, then BOBX. The first row exposes length 3, substring XY, and concatenation ADAX. Three inner predicate values occupy the normal parsed value slots, proving the independently packed projection literals survive every ORDER and exact DISTINCT replay.

The inner WHERE owns a separate postfix Boolean program:

SELECT C.ID FROM CUST AS C
WHERE EXISTS (
  SELECT O.ID FROM ORDR AS O
  WHERE O.CID=C.ID
    AND (O.TOTAL>60 OR O.TOTAL<0)
    AND NOT (O.ID=14)
);

It returns customers 1 and 2. Outer predicates compose normally with the subquery term, including CHAR LIKE and named enum member predicates.

IN, NOT IN, CHAR, enum, and fixed-point cases are target-tested:

SELECT C.ID FROM CUST AS C
WHERE C.ID IN (
  SELECT O.CID FROM ORDR AS O
  WHERE O.CID=C.ID AND O.TOTAL>=0
);

SELECT C.ID FROM CUST AS C
WHERE C.NAME IN (SELECT O.LABEL FROM ORDR AS O WHERE O.ID=10);

SELECT C.ID FROM CUST AS C
WHERE C.STATE IN (
  SELECT O.STATUS FROM ORDR AS O
  WHERE O.CID=C.ID AND O.STATUS=STATE.ACTIVE
);

SELECT C.ID FROM CUST AS C
WHERE EXISTS (
  SELECT 1 FROM ORDR AS O
  WHERE O.CID=C.ID AND O.AMOUNT>=2
);

Each returns customer 1. An IN input containing only NULL produces UNKNOWN and no row. NOT IN over a set containing NULL also produces no false-positive row.

The combined three-schema enum case uses a joined outer producer and resolves the member against the correlated third source:

SELECT C.ID
FROM CUST AS C JOIN ORDR AS O ON C.ID=O.CID
WHERE EXISTS (
  SELECT 1 FROM ORDR AS X
  WHERE X.ID=O.ID AND X.STATUS=STATE.ACTIVE
);

Only the joined order whose third-source row is active qualifies, so the result is customer 1. This exact query runs in both Peddle REU sizes and the join VICE lane.

Scalar subqueries distinguish zero, one, and multiple rows:

SELECT C.ID FROM CUST AS C
WHERE C.ID = (
  SELECT O.CID FROM ORDR AS O WHERE O.ID=10
);

SELECT C.ID FROM CUST AS C
WHERE C.ID = (
  SELECT O.CID FROM ORDR AS O WHERE O.CID=C.ID
);

The first returns customer 1. The second encounters two rows for customer 1 and rsql_cursor_next() returns RSQL_ERR_SUBQUERY_ROWS. Empty scalar input is NULL/UNKNOWN. Incompatible selected types such as CHAR IN (SELECT I16 ...) are rejected during binding.

ORDER BY, DISTINCT, LIMIT, and OFFSET

The result-shaping lane inserts five deliberately unordered rows with duplicate CHAR values, duplicate numeric values, signed I8 extremes, NULLs, enum values, and Commodore FLOATs. These queries verify ordinary ascending and descending order:

SELECT ID FROM SRT ORDER BY ID;
SELECT ID FROM SRT ORDER BY ID DESC;
SELECT ID FROM SRT ORDER BY CODE;
SELECT ID FROM SRT ORDER BY NAME ASC, ID ASC;
SELECT ID FROM SRT ORDER BY VALUE ASC, ID DESC;

The expected ID sequences are (1,2,3,4,5), (5,4,3,2,1), (3,4,2,5,1) for signed I8 values -128,-1,0,10,127, (1,3,4,5,2) for folded CHAR ordering, and (5,1,4,2,3) for FLOAT with NULL first in ASC order.

Compound keys and NULL direction are covered explicitly:

SELECT ID FROM SRT ORDER BY SCORE ASC, ID DESC;
SELECT ID FROM SRT ORDER BY SCORE DESC, ID ASC;

These return (4,5,3,2,1) and (1,2,3,5,4). ASC places NULL first; DESC places it last; the ID key deterministically orders equal SCORE values.

Filtering, qualification, and both LIMIT/OFFSET spellings compose with order:

SELECT ID FROM SRT
WHERE ACTIVE=TRUE AND NAME NOT LIKE 'G%'

Scalar expressions in grouped aggregate results

The ordinary producer combines packed literal metadata, grouped keys, scalar evaluation, and an aggregate in one cursor:

SELECT LENGTH(K),SUBSTR(K,1,1),K||'!',COUNT(*)
FROM D
GROUP BY K;

For D = ('BY'),('BY'),('Z'), the rows are (2,'B','BY!',2) and (1,'Z','Z!',1). The same test deliberately combines a literal-bearing scalar with GROUP BY so the shared descending parser pool is exercised.

Two-source and direct three-source aggregate producers exercise source-to- source concatenation:

SELECT LENGTH(X.K),X.K||Y.K,COUNT(*)
FROM D AS X CROSS JOIN E AS Y
WHERE X.K='BY'
GROUP BY X.K,Y.K;

SELECT LENGTH(A0.K),A0.K||Z.K,COUNT(*)
FROM D AS A0
JOIN E AS Y ON Y.K='AX'
JOIN F AS Z ON Z.BID=Y.ID
GROUP BY A0.K,Z.K;

The first returns BYAX/4 and BYLM/2; the second returns BYBY/4 and ZBY/2. An ungrouped literal is also valid:

SELECT 'G',COUNT(*) FROM D;

It returns ('G',3). In contrast, SELECT LENGTH(K),COUNT(*) FROM D is rejected because K is neither grouped nor aggregated.

The ordinary grouped comparator orders and deduplicates computed scalar values rather than their source columns:

SELECT K||'!',COUNT(*) FROM D GROUP BY K ORDER BY 1 DESC;
SELECT DISTINCT 'G' FROM D GROUP BY K;

The first returns ('Z!',1) then ('BY!',2). The second sees two physical groups but emits one logical row, ('G'). Direct three-source aggregate replay also orders a composed projection:

SELECT LENGTH(A0.K),A0.K||Z.K,COUNT(*)
FROM D AS A0
JOIN E AS Y ON Y.K='AX'
JOIN F AS Z ON Z.BID=Y.ID
GROUP BY A0.K,Z.K
ORDER BY 2 DESC;

It returns ('ZBY') before ('BYBY'). Two-source joined pair replay is tested with a source-to-source concatenation whose second operand used to collide with aggregate ORDER scratch:

SELECT X.K||Y.K,COUNT(*)
FROM D AS X CROSS JOIN E AS Y
WHERE X.K='BY'
GROUP BY X.K,Y.K
ORDER BY 1 DESC;

It returns ('BYLM',2) then ('BYAX',4). Exact DISTINCT over multiple joined groups is independently checked by:

SELECT DISTINCT LENGTH(X.K)
FROM D AS X CROSS JOIN E AS Y
WHERE X.K='BY'
GROUP BY X.K,Y.K;

Both groups evaluate to 2, so exactly one row is emitted. Correlated aggregate scalar replay is covered for both shaping operations:

SELECT DISTINCT 'G'
FROM D AS X
WHERE EXISTS(SELECT 1 FROM F AS Y WHERE Y.K=X.K)
GROUP BY X.K;

SELECT X.K||'!',COUNT(*)
FROM D AS X
WHERE EXISTS(SELECT 1 FROM F AS Y WHERE Y.K=X.K)
GROUP BY X.K
ORDER BY 1 DESC;

The DISTINCT form emits one G across the qualifying BY and Z groups; the ordered form emits ('Z!',1) then ('BY!',2).

Finally, grouped scalar output is materialized and read back through CTAS:

CREATE TEMP TABLE GS AS
SELECT LENGTH(K),K||K,COUNT(*) FROM D GROUP BY K;

SELECT * FROM GS ORDER BY C1 DESC;

The destination derives C2 as fixed CHAR(6), so its public table read contains BYBY or ZZ followed by physical trailing spaces. This distinguishes logical scalar cursor length from materialized fixed-width CHAR semantics.
